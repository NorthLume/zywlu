# ADR-0001：采用 Astro 的静态优先主页架构

- 状态：已接受
- 日期：2026-07-30
- 决策者：项目维护者

## 背景

ZYWLU 首阶段是内容与品牌导向的主页，核心诉求包括：

- 首屏加载快，搜索引擎和分享预览易于理解。
- 移动端、桌面端、键盘操作和辅助技术体验完整。
- 在 Ubuntu 24.04 LTS 服务器上通过 Nginx 稳定托管。
- 初期运维简单，同时给未来的局部交互和数据能力留出升级路径。
- 浏览器端 JavaScript 体积与长期依赖成本保持可控。

## 决策

1. 使用 Astro 作为站点框架，默认生成静态 HTML。
2. 使用 TypeScript 严格模式编写配置和交互逻辑。
3. 页面默认零客户端脚本；只有明确需要交互的组件才引入交互岛。
4. 首版使用原生 CSS 和集中式设计令牌，组件框架按实际交互需求引入。
5. 使用 npm 与锁文件保证依赖安装可重复。
6. 使用 ESLint、Prettier、Astro Check 和 Vitest 组成基础质量门槛。
7. 生产构建输出 `dist/`，由 Nginx 直接托管。
8. 动态能力出现时，优先增加边界清晰的 API 服务；服务端渲染需求达到门槛后再通过新 ADR 评估 Astro 适配器。

Astro 官方文档说明静态站点无需服务端适配器，并提供标准的 `src/`、`public/`、
`astro.config.mjs` 与 `tsconfig.json` 项目结构：

- <https://docs.astro.build/en/guides/integrations-guide/node/>
- <https://docs.astro.build/en/basics/project-structure/>

## 备选方案

### 纯 HTML、CSS 与 JavaScript

依赖最少，但随着页面、组件和内容增加，复用、路由、构建优化与类型检查需要自行维护。

### React 或 Next.js 全站应用

生态成熟，适合复杂应用；首阶段会引入高于内容主页所需的客户端和运行时复杂度。

### 常驻 Node.js 服务

便于即时动态渲染，但增加进程管理、资源占用和运行时故障面，当前需求尚未体现相应收益。

## 结果

### 正向结果

- Nginx 可直接托管构建产物，发布与回退路径简单。
- 页面默认输出完整 HTML，利于性能、SEO 和渐进增强。
- 可在单个组件层面引入交互，而非升级整个站点运行模型。
- TypeScript 与统一质量脚本让本地和 CI 使用相同验证流程。

### 代价

- 强依赖实时个性化的页面需要额外 API 或渲染层。
- 团队需要熟悉 `.astro` 组件语法与内容集合约定。
- 引入第三方交互框架前需要评估客户端体积和维护成本。

## 复审触发条件

出现以下任一情况时创建新 ADR 复审本决策：

- 登录态、权限或个性化内容成为主页核心能力。
- 多数页面依赖请求时数据，构建期生成失去主要优势。
- 后台内容预览要求与静态发布流程发生持续冲突。
- 交互岛之间共享大量客户端状态，当前边界开始增加复杂度。
